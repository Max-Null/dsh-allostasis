## 结论

**这场会话不是「自己」崩的，是被一行展开调用打死的 —— 而且打死之后再也起不来。**

- `src/thinking.ts` 的 `latestThinking()` 用 `parts.push(...record.texts)` 拼接推理文本，
  而 `texts` 的元素数**等于该步的输出 token 数**（DSH 把每个流式增量无损存成一条）。
  引擎对一次展开调用的实参个数有上限，本机实测 **约 12.5 万**（§2.3）。t14/s4 那一步产出了
  **210,139** 个增量 → 抛 `RangeError: Maximum call stack size exceeded`。
- 该函数挂在 `agent/pre-step` 上（`src/index.ts:206,209`），**每个 step 都要跑**。于是 turn 14
  当场以 error 收尾；用户再发一句话（turn 15），turn 在 **38 ms** 内同样报错 ——
  **连一个 `step/start` 都没产生**。
- 自锁由此成立：要跳出这个状态，需要有**新的一条更短的助手消息**来覆盖「最近一条思考」；
  但产生新消息要先过 `pre-step`，而 `pre-step` 每次都死在同一步。**压缩救不了** —— 事件流是
  append-only，压缩改的是模型上下文，改不了 `snapshotEvents()` 的视野（§4.2）。
- 退化提醒**一次都没发出**，而它本该在 t14/s4 之后立刻发出：t13/s8（重复率 98.5%）与
  t14/s4（99.7%）刚好凑满「窗口累计 2 次越线」的触发条件（§4.3）。

一次越线加一个异常回合，就足以让整场会话永久失去响应能力。**就本机的会话库（483 个会话）
而言，这是第一例「插件把会话弄成不可恢复状态」的事故**，与前面几次「提醒该发没发」
不是同一类问题。

## 二、取证方法与工具

### 2.1 一条会误导人的判据：字符串搜索

**不能用「日志里出现了多少次报错文案」来判断谁崩过。** 正在做取证的那个会话自身会把
这段文案写进推理与工具输出：实测一个 0.35 MB 的分析会话贡献了 92 次命中，而它的
`turn/end` 异常次数是 **0**。

判据只认结构化事件：`turn/end` 的 `data.reason.kind === 'error'`，再交叉
`assistant/message` 的 `data.usage.outputTokens` 量级。本次全库普查里，18 个会话的日志
含这段文案，真正因它崩掉的只有本案（及其 fork，见 §2.4）。

### 2.2 决定性实验：装版产物 + 真实日志

结论不是推断出来的，是把**装版真实产物**喂**真实会话事件**跑出来的：

```sh
node .ssid-iso-test/forensics/10a2785f/verify-thinking.mjs
```

| 输入 | 结果 |
|---|---|
| `dist/thinking.js` 的 `latestThinking` + 全量 1734 条事件 | **抛 `RangeError: Maximum call stack size exceeded`** |
| 同一份产物 + 剔除 seq ≥ 1719 的事件 | 正常，返回 t14/s3 的 2,433 字符 |
| 同一份产物 + 只喂 seq ≤ 1690 的事件 | 正常，返回 t13/s9 的 1,457 字符 |
| 逐元素 push 的等价实现 + 全量事件 | 正常，读回完整的 368,074 字符 |

这四行排除了「模型的问题」与「日志的问题」；「别处也有同样的写法」由检索排除 ——
`max-null-plugins` 全域只有 `thinking.ts:37` 这一处把外部数据展开进函数调用，
内核侧的 `expandAssistantStream` 走的是逐元素 push（§七）。**只有那一步、只有那种写法会崩。**

### 2.3 上限测定

引擎不暴露这个常量，只能二分探出来。多次独立测量落在 **124,642–124,883** 之间：

| 测量 | 结果 |
|---|---|
| `repro.mjs`（二分，`push(...arr)`） | 124,883 |
| `tools/audit-chunk-limits.mjs --limit`（两次） | 124,870 / 124,642 |
| 同一支工具在跨会话扫描里（三次） | 124,784 / 124,792 / 124,672 |

**极差 241**（与调用点形态、栈上已有深度、JIT 状态有关），所以「12.5 万」应当被当作数量级
而不是精确阈值 —— 工具因此每次运行都重新探测，不写死常量。本案的 210,139 是其 1.68 倍，
抖动不影响判定。

### 2.4 跨会话普查

`node tools/audit-chunk-limits.mjs --root ~/.dsh/sessions-ssid --min-size 1MB`（历次运行测得的

- 扫描 **483 个会话文件**，**越线 2 个**：本案与它的 fork `session-7a4a0803` —— 同一份
  210,139 个增量，两者的 `turn/end` 异常分别是 2 次与 3 次。
- **最接近而未越线的是 `session-fabc21b2` 的 t77/s19：120,061 个增量，占上限 96%** ——
  差约 4,800 就跨过去（§3.1）。
- 其余进表的会话最大只有 12%，它们**是因为有 `turn/end` 异常**才被列出来的，与这个上限无关；
  工具对此有单独标注，见 §2.5。

### 2.5 `tools/audit-chunk-limits.mjs`

```sh
node tools/audit-chunk-limits.mjs <session.v4.jsonl|.jsonl.zstd> [--top N]
node tools/audit-chunk-limits.mjs --root <dir> [--min-size 1MB]
node tools/audit-chunk-limits.mjs --limit
```

它报三件事：**本机实测上限**、**各步的增量数与占上限比例**、**以 error 结束的回合**。
越线与异常回合同时出现时，会额外提示「该会话可能已进入每步都失败的自锁状态」。

跨会话模式按**三态**标注每个进表的会话：`越线`、`接近上限`、`异常回合 ×N（与上限无关）`。
第三种必须与第二种分开 —— 把「只是有异常回合」标成「接近」，读者会以为余量紧张，
而这正是 §2.1 那种误读的另一种形态。

退出码：0 = 未越线；1 = 有会话越线；2 = 用法错误或读取失败。

**它不 import `src/` 的判据** —— 与 `tools/audit-loop-detection.mjs` 的区别就在这里：
这次的判据（引擎实参上限）不是插件的配置项，而是运行时属性，所以工具自己探测、自己报口径。

## 三、证据

### 3.1 边界对照：三个真实数据点夹住上限

| 步 | 增量数 | 占上限 | 重复率 | 结果 |
|---|---|---|---|---|
| t13/s8（本会话） | 25,322 | 20% | 98.5% `loop` | 未越线，正常收尾 |
| **`fabc21b2` t77/s19** | **120,061** | **96%** | — | **未越线（差约 4,800）** |
| t14/s4（本会话） | **210,139** | **169%** | 99.7% `loop` | **抛 RangeError → 会话锁死** |

中间那一行是本案之外最重要的证据：**这个坑不是理论上的** —— 另一个会话已经跑到离上限 4%
的位置而没有触发，说明该现象在真实的退化会话里是可复现地接近的，只是那次运气好。

### 3.2 触发条件是 `maxTokens` 与退化的乘积

单步输出的增量数等于该步的输出 token 数，所以**能否触发这个坑，取决于本机允许模型
一次输出多少**：本机 `maxTokens = 256,000`，而正常步只有几千 token —— 只有退化把它推到
五位数以上才可能接近 12.5 万。反过来，`maxTokens` 配得小的环境根本够不着（这是 §5.3
候选 D 的依据）。

### 3.3 应变三条线在本案的实绩

取证顺带量到了这个插件的工作记录（判据用装版 `dist/drift.js` / `dist/repetition.js` 复算）：

| 能力 | 出手 | 效果 |
|---|---|---|
| 一期 · 语言漂移锚定 | 4 次，全部投递达模型 | **4/4 看到密度回落**：32.5%→4.0 / 17.2%→0.0 / 16.9%→3.7 / 22.4%→（23.5% 再提醒）→11.4→4.7 |
| 空回合检测 | 2 次判定成立 | t13/s8 那次投递成功，模型补上 212 字文本；t14/s4 那次进队列后**从未投出** |
| 二期 · 推理退化提醒 | **0 次** | 见 §4.3 |

这张表同时是一份**反证**：0 条退化提醒不是「插件没加载」或「`pre-step` 没跑」——
另两条线在同一个 `pre-step` 钩子里一直在工作。

## 四、根因

### 4.1 直接原因：把外部数据的长度当成了函数参数个数

```js
// 修复前（src/thinking.ts:37）
for (const record of event.data.stream) {
  if (record.type === 'reasoning-chunks') parts.push(...record.texts)
}
```

`record.texts` 来自会话日志，长度由模型的输出决定 —— 它是**不可信数据**，却被展开了。
展开调用把每个元素变成一次实参传递，元素数超过引擎上限即抛 `RangeError`。

### 4.2 为什么是「锁死」而不是「一次失败」

三条性质叠在一起，把一次异常升级成了不可恢复：

1. **调用频率**：`agent/pre-step` 每个 step 都跑，而 `latestThinking()` 是钩子里的第一件事
   （`src/index.ts:209`）。
2. **取样会一直命中它**：`latestThinking()` 从事件流倒扫，取「最近一条非空的思考」——
   而那条 36.8 万字的推理正是最近的一条。它不会因为时间流逝而消失。
3. **压缩改不了取样视野**：`snapshotEvents()` 返回的是 append-only 的事件流；压缩替换的是
   送给模型的上下文，不删事件（`compaction/end` @ seq 1727 之后 turn 14 立刻报错，
   就是这一步的实测证据）。

于是形成自锁：**要产生新消息必须先过 `pre-step`，而 `pre-step` 每次都在同一条旧消息上失败。**

### 4.3 退化提醒为什么一次都没发出

按 `trackLoop`（窗口 5 步、累计 2 次），本案本该触发一次：

| 步 | 重复率 | 判定 | 窗口内命中 | 是否触发 |
|---|---|---|---|---|
| t13/s8（17:37） | 98.5% | `loop` | 1 | 否 |
| t13/s9 ~ t14/s3 | 均 normal 或 insufficient | — | 1（`insufficient` 不记命中） | 否 |
| **t14/s4（22:30）** | **99.7%** | **`loop`** | **2** | **本该触发** |

t13/s8 与 t14/s4 之间隔了 **4 小时 53 分**（窗口按步数累计，不按时间），所以两次命中确实
落在同一窗口里。

**而它没有发出，因为触发需要的那次读数就是崩溃点**：`latestThinking()` 在 `measureRepetition()`
之前执行，抛错时判据还没算出来。**退化提醒被它要检测的那个样本打死了。**

### 4.4 更值钱的一条：已有原则没有贯彻到 `pre-step`

这个仓库里已经写下了正确的原则 —— `installSilentTurn` 的注释（`src/index.ts:129-131`）：

> 内核的契约测试写明该事件里抛出的异常会让 turn 以 error 结束……**判据失败不得升级成回合失败**。

空回合那一侧因此整段包了 `try/catch`，连 `agent.steer` 都单独再包一层。**但 `pre-step`
那个钩子没有包**（事发时为 `src/index.ts:206-229`），于是「判据失败」在这里就地升级成了
「会话锁死」。（**当前状态**：已按同一条原则补上，见 §5.1。）

这不是新知识，是一条**已经知道、只在一个挂载点上落实**的约束。它比 spread 那一行更值钱：
spread 修掉的是这一次崩在哪，`try/catch` 挡掉的是整类「判据出错 → 会话报废」。

### 5.3 修复候选（供迭代决策）

**候选 A：`pre-step` 钩子整段包 `try/catch`（已落地，见 §5.1）**

实现照搬了 `installSilentTurn` 的形状，但有一处不同：`await next()` 留在 `try` 之外 ——
那是内核的职责，本插件不该吞掉它的失败。`try` 只盖住「取数 + 度量 + 两条判定 + 组装」。

**候选 B：取数与判据解耦（A 已覆盖，不再单独立项）**

两条线共用同一次 `latestThinking()`，这在结构上无法用 `try/catch` 分开 —— 取数失败时两边
都没有输入。A 落地的降级（这一步不判定、窗口状态不推进，等价于 `insufficient`）已经是这个
形状下的正确处理。

**候选 C：给二期判据一次公平检验**

本案对二期判据**什么都没有证明**（§4.3）。现成的真样本有三个：
`fabc21b2`（120,061 增量）、`be06f388`（t61/s3 重复率 97%）、本案 t14/s4（99.7%）。
用 `tools/audit-loop-detection.mjs` 离线复算即可回答「提醒会在第几步发出、发得及来不及」。

**候选 D：把上限写进配置或在读取侧截断**

`texts` 的长度既然由 `maxTokens` 与本机上限共同决定，可选的做法是给
`latestThinking()` 加一个长度上限（超过就只取尾部 N 个增量 + 标记截断）。**代价是判据
口径改变**（重复率会算在被截断的文本上）——需要先想清楚判据要的是「模型想了什么」还是
「最后想了什么」。**在没有数据支撑之前不建议落。**

**候选 E：处理「读事件流」与「模型实际可见」的脱钩**

`latestThinking()` 读的是事件流，而压缩改的是模型上下文 —— 两者在压缩之后就不一致了。
后果有两个：误报（对模型已经看不见的旧样本反复判定）与本案的锁死（压缩明明发生了，
取样视野一丝不变）。**修法需要设计取舍，不在本次范围内。**

> **后续（2026-10-07）**：本次事故另引出了一条不在这五个候选里的路——**在生成过程中掐断**。
> 它的设计已定案，见 `docs/设计/2026-10-07-应变三期-生成中掐断与重定向.md`：动机是本案
> §1.2 的曲线形状（退化的决定点在头 5 千字符内完成），方案吸收了生态里现成的
> `dsh-repeat-guard` 机制，判据复用本插件的统计口径 + 一张白名单表。

### 5.4 已验证（2026-10-07）：目标会话已恢复

**这是本案唯一真正重要的验收**：那个当初被锁死的会话，现在还能不能用。

```
turn 14  2026-10-06 22:30   步4 产出 [reasoning] 368,074 字
         → turn/end = {"kind":"error","error":{"message":"Maximum call stack size exceeded"}}   ✗
turn 15  2026-10-06         （无用户输入、自动续跑）→ 38 ms 内同样 error                        ✗
turn 16  2026-10-07 03:25   用户「你好」→ 助手正文 2,793 字 → {"kind":"completed"}               ✓
```

**为什么这一轮成功就等于修复生效**：在 0.3.0 下，**每一个后续步骤**都会在 `agent/pre-step`
取样时撞上那条 368,074 字的思考、招展开调用爆栈（turn 15 连用户输入都没有就 38 ms 失败，
正是这个形状）。0.4.0 修的恰好是这两处 —— **turn 16 能跑完，说明 `pre-step` 不再抛**。

**装版侧的同步链路**：0.4.0 发布 → `profile-template` 的 pin 改到 0.4.0（`e074402`）→
装版随包插件集的实体替换（`dist` 29 文件、逐文件 SHA 与源一致；运行时 profile 那一处是
Junction，指向同一实体，因此一并更新）→ 重启。

**顺带一条对本案有价值的现场**：同一个会话的 turn 13 也退化过（步 8 产出 `[reasoning]`
**55,165 字**），而它**被空回合兜底接住了**：注入「⚠️ 空回合（应变）」之后，步 9 正常收尾。
也就是说，二期那个能力在同一个会话里已经救过一次场，而 turn 14 那次的规模（368,074 字，
是它的 6.7 倍）大到兜底接不住。**这正是三期「在生成过程中掐断」要补的位置**（设计文档 §一）。

**边界（别误读这条验证）**：0.4.0 保证的是**退化不会再锁死会话**（读取侧不再爆栈）。
**退化的产生本身仍在** —— `streamCut` 默认 `observe`（只观察、不掐断），所以默认配置下
下一次退化仍会烧掉同样的 token，只是不会再把会话弄成打不开。要拦住它得显式开 `cut`。
