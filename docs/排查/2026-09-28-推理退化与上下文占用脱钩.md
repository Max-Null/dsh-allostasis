# 推理退化与上下文占用脱钩：一次 19 轮会话的实测

> 状态：**结论已定 · 待设计采纳** · 2026-09-28
> 触发：用户观察到「上下文只用了 37%，助手的思考却中断了」——直觉上上下文没满就不该出问题。
> 结论：**退化出在模型生成侧，且与上下文占用没有可用作判据的关系**。压缩能减少 token，但改变不了退化率。
> 影响面：`docs/设计/2026-09-20-应变-设计方案.md` §2.2（以「占用 76% 时开始漏掉已确认的事实」为据推出高保真任务的落盘时点）与 §13.3（把「何时该提醒」归给 preset 阈值）。本次实测说明**占用本身不具备判据效力**，两处的论证前提都需要重新审视。

## 一、现象

会话进行到中段，助手的一条思考是这样结束的（用户截图，思考面板原文）：

```
做。
好。
执行。
好。
做。
好。
（输出）
好。
做。
好。
我在循环。直接输出。
好。
做。
（查测试 + PinConflictsWithArchive）
好。
做。
```

界面上没有任何报错、没有重试、没有中断提示。用户在那一刻看到的上下文占用读数：**37%**。随后用户手动触发压缩（界面提示「已压缩 408 条历史记录（约 196899 tokens）」）。

三个需要分开回答的问题：

1. 那段输出是**被谁打断**的？
2. **37%** 这个读数意味着什么？
3. 这属于 DSH 端的问题还是 LLM 端的问题？

## 二、方法

会话日志是唯一能回答「模型当时看到了多少上下文、输出了什么」的证据源。DSH 遵循「model-visible ⟺ logged」，每次请求的 provider usage 与完整流式输出都落在 `session.v4.jsonl.zstd` 里。

取数口径：

| 量 | 定义 | 来源 |
|---|---|---|
| 上下文压力 | `inputTokens + cacheReadTokens + cacheWriteTokens` | `assistant/message` 的 `data.usage`（provider 上报的真实计数） |
| 窗口 | 1,000,000 | `request/context` 事件的 `contextWindow` |
| 推理文本 | `data.stream[]` 中 `type: 'reasoning-chunks'` 条目的 `texts` 数组 | 同前 |
| 重复率 | 推理文本按换行与中英句读切分后，**出现 ≥3 次的单元**占全部单元的比例 | 派生量 |
| 界面读数 | `projectedTokens ?? pressureTokens` 除以 `contextWindow`，上限 100% | `packages/client/ui-conversation/src/client/context-occupancy.ts:18-21` |
| 窗口来源 | `request/context` 事件的 `contextWindow` | 同前（本会话 seq=13，值 1,000,000） |

压力与推理文本的取法与本插件 `src/thinking.ts`、官方 `packages/llm/token-meter/src/usage-projection.ts` 的 `pressureFrom` 一致。

## 四、结论

### 4.1 退化与上下文占用脱钩

用户看到的 **37.0%** 精确对应 t18（369,610 token）——读数本身没有错。但**同一时刻的推理重复率是 81%**。

更能说明问题的是 t12：压缩刚把占用从 67.9% 砍到 **26.1%**，重复率是 **84%**——比压缩前的 83% 还高。

**占用不是开关，也不是线性因子。**在本次会话里，26% 和 68% 的退化程度没有可区分的差别。

### 4.2 压缩不是解药

第一次压缩把压力从 678,278 降到 261,269（**−62%**），而随后六轮（t12–t17）的重复率稳定在 80%–87%，与压缩前的 68%–92% 同量级。

压缩减少的是 token 数量。退化是**生成过程的采样塌陷**，诱因在推理链的形态，不在 token 数量。**「把压缩阈值调低到退化区之前」这条处置思路，在本次实测中不成立**——它只是让压缩来得更早，而压缩本身治不了这个病。

### 4.3 模型知道自己循环，但停不下来

截图里有一行 **「我在循环。直接输出。」**——模型明确识别出了自己处在循环中，标记了它，**然后继续循环**（`好。/ 做。/` 又重复了三轮才结束）。

这条观察对本插件尤其重要：**退化不是「不知道」，是「知道了也停不下来」。**模型自身的位置无法执行终止动作——它只能在生成里写下一句「我该停了」，而那句话本身也是生成的产物。

因此**外部干预可能是唯一出路**：一个在生成之外、能在下一次请求之前改变条件的信号。

### 4.4 归因：生成侧，不是内核侧

| 归属 | 判断 | 依据 |
|---|---|---|
| 退化的**产生** | **LLM 端（生成侧）** | 请求成功返回，日志无失败、无重试、无中断事件 |
| DSH 端的**记录** | 忠实 | 推理原文完整落盘，正是本次分析的数据来源 |
| DSH 端的**检测** | **不存在** | 在 `packages/core` 中检索 `repetition` / `degenerat` / `loop-detect` 等模式，仅有 `agent/status repeated` 这类无关命中 |
| DSH 端的**中断** | 未发生 | 全部 18 条 `turn/end` 的 reason 均为 `completed` |

所以「修 DSH 端」的准确含义**不是修一个内核缺陷**——内核在这里没有坏。准确的含义是：**在内核之外补一个观测与干预层**，把「模型正在打转」变成系统可响应的事件。那正是本插件的定位。

顺带排除一个猜测：**不是 maxTokens 触顶**。单次请求输出上限 256,000，而每条推理只有 1,000–2,600 字符，差两个数量级。

## 五、对既有结论的修正

### 5.1 长会话输出退化（2026-09-18）

`seek-soul-in-darkness/docs/排查/2026-09-18-长会话输出退化.md` 记录「约 67 万 token 起出现明确信号」，处置是把压缩阈值从 0.8 调到 0.5，隐含推论是「压缩线压到退化区之前即可」。

本次实测证伪了该推论的后半段：**t4 在 56.8% 就退化到 90%**，而压缩到 26.1% 之后重复率仍是 84%。**阈值调整与退化率之间没有观察到因果关系。**

### 5.2 本插件设计文档

**§2.2**（第 43–45 行）以一条实证为据推出占用设定点：「占用为 76% 时助手开始漏掉已确认的事实」，进而得出「高保真任务在 65% 就该开始落盘」。

本次数据不支持「占用是退化前提」这一环：**26.1% 的占用下重复率 84%**。那条 76% 的观察本身没问题，但把它归因给占用，很可能混淆了两个独立变量——**当时的会话同样处在长推理链 + 高密度工具调用的形态中**。t19 提供了一个反向对照：同一会话、占用更低，换成取证类任务（每步有外部输入）后重复率立刻降到 **8%**。

**这是观察到的关联，不是已证实的因果**，但足以要求把「占用」从退化判据的候选位置上撤下来。§2.2 否决固定阈值的论证本身仍然成立——需要修正的是它给出的替代品：**不该换成另一个标量阈值**。

**§13.3** 的两条理由各自有了新答案：

- **① 说「算比例需要 `contextWindow`，而这个值不在插件手边」**——该待查项已可关闭：`request/context` 事件带 `contextWindow` 字段（本会话 seq=13，值 1,000,000），会话中途换模型会再发一条。host 侧插件订阅事件即可，无须绕到适配器配置或 provider 元数据。
- **② 说「『什么时候出现』取决于 preset，插件写死任何百分比，换个 preset 就错位」**——本次实测给出的结论比这更强：**不是「阈值该定在多少」的问题，而是「占用这个量不适合当判据」**。一个与退化率没有可区分关系的量，无论阈值放在哪都得不到好的触发时机。

§13.3 的处置结论是「先只做读数、不做注入」，与本次建议同向，见 §6.4。

## 六、对 dsh-allostasis 的意义

### 6.1 数据源与通路都已在手

现成的实现覆盖了这条能力的全部难点：

| 环节 | 现状 | 位置 |
|---|---|---|
| 拿到推理全文 | **已有** | `src/thinking.ts` —— 读 `assistant/message` 的 `reasoning-chunks.texts` |
| 每步被回调 | **已有** | `src/index.ts` —— `agent/pre-step`，带 `turn` / `step` |
| 判据可插拔 | **已有** | `src/drift.ts` —— `measureThinking` / `verdict` 的形态可直接复用 |
| 近因注入 | **已有** | `src/anchor.ts` + `createUserMessage`，追加到请求末尾 |
| 节流 | **已有** | `src/throttle.ts` —— 同一 turn 至多一次 |

**新增的只是一个判据函数**：把「英文功能词密度」换成「重复率」，其余通路原样复用。

### 6.2 能力候选：退化检测（思考重复率）

与中文锚定同构：**平时不出现、退化时才出现**。逐条对齐：

- **判据**：单条推理按句读切分后，出现 ≥3 次的单元占比 ≥ 阈值。本次会话的可用区间：中文正常期 ≈ 0–35%，退化期 68%–92%（阈值候选 50%）。
- **注入文本**：复用 `anchorText` 的措辞结构——说清是哪一步、重复了多少、最高频的单元是什么。**给出具体碎片比给出比例更有用**：`好`×143 这种信息能直接告诉模型它在写什么。
- **节流**：沿用 `throttle.ts`。退化与语言漂移一样具有持续性，不节流会连成串（§12.4 已实测过这个形态）。
- **注入位**：近因位置，与中文锚定一致。

### 6.3 边界

**它只能影响下一次，不能阻止当次。**`agent/pre-step` 在上一步的推理已经输出之后才被调用，那一轮的打转已经发生。这个能力的作用是**缩短退化的持续轮数**，不是消除单次退化。

**它与压缩无关，不要挂在一起。**本次数据已经说明压缩对退化率无效；把两个动作耦合会让归因重新变模糊。

### 6.4 待验证

**中文锚定有效，不证明重复锚定有效。**

中文漂移是「用错了语言」——纠正一句话就能把语言模式拉回来，实测有效（本会话期间就触发过一次，模型随即回到中文思考）。重复退化是「推理塌陷」——模型已经写出「我在循环」却仍然继续，说明它**能识别、不能执行终止**。

所以关键问题是：**一条外部的、在下次请求前到达的提醒，能不能改变采样轨迹？** 这需要实验，不能靠类比推断。设计上应先做成**只观测不干预**的形态（记录退化事件、暴露读数），拿到足够样本后再决定注入文本与时机——与 §13.3 对上下文占用采取的「先只做读数」是同一个推进节奏。

## 七、复现方式

```sh
# 单会话退化报告（压力峰值、重复率、压缩点）
node seek-soul-in-darkness/shell/scripts/session-degeneration-scan.mjs <session.v4.jsonl.zstd>

# 跨会话扫描
node seek-soul-in-darkness/shell/scripts/session-degeneration-scan.mjs --root ~/.dsh/sessions-ssid --min-size 3MB
```

取本报告第三张表（按轮折叠的压力 / 重复率对照）需要额外一步分组，`session-degeneration-scan.mjs` 目前只给峰值与 Top N，**逐轮对照表尚未固化进脚本**。

两个已知的取数陷阱：

1. **会话文件是 `session.v4.jsonl.zstd`**，不是 `v3`。按 `v3` 精确匹配会漏掉当前所有会话。
2. **扫描脚本把压缩阈值硬编码为 `0.8 × 窗口`**，报告里印出的「自动压缩阈值」一行不读 profile 配置，与本机实际触发点不符。

## 八、遗留问题

1. **退化的诱因到底是什么？**本次只有一条对照观察（t19 换任务形态后重复率 12.7% → 8%），不足以定因。需要跨会话找「低占用也退化」「高占用不退化」的样本。
2. **逐轮压力 / 重复率对照表**值得固化进扫描脚本——本次是靠一次性脚本算的。
3. **压缩后的上下文成分**没有量化：408 条记录压成一份摘要，剩下的高密度工具结果与摘要是否本身就是退化的土壤，本次未验证。
4. **本报告的数据口径**（句读切分的 ≥3 次单元占比）是启发式。绝对值会随切分规则变化，**只能在同一判据下横向比较**。
