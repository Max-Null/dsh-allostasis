# 补块的落盘形状 —— 掐断后的 `assistant/message` 与真实正常收尾的字段级对照

> **给下一个会话的接手说明**：本报告自包含。§五 分开标注了「实测」「读代码确证」「未验证」。
> 结论一句话：**补块让块形状与真实收尾一致，但有两处字段差异补不出来**（`data.usage` 与
> `message.source.replayState`），二者都来自上游适配器、掐断时根本没产生。

## 结论

**「补 `block-end` + `finish{stop}` 伪装成正常结束」在块形状上成功，在字段上留了两处可检出的痕迹。**

| 面 | 判定 |
|---|---|
| `message.content` 的块形状 | **一致**——纯 reasoning 的正常收尾本来就存在（对照条 seq 718），补块产出的正是同一种块序列 |
| 步骤级收尾形状（`step/end`、`turn/end`） | **一致**——掐断步的 `step/end` 键同为 `turn,step`，所在 turn 的 `turn/end.reason` 仍是 `{kind:"completed"}` |
| `data.stream` 的记录序列 | **有差异**——掐断条少一格 `chunk:usage`，且 `finish` 格不带 `replayState` |
| `data.usage` | **缺字段**（真实收尾必有，含自然产生的纯 reasoning 收尾） |
| `message.source.replayState` | **缺键**（同时 `message.source` 的 JSON 从 247–263 字符降到 71 字符） |
| 落盘自洽性 | **无破绽**——内核的种子校验拿落盘字段与从 stream 重放的组装器对比，掐断条两边同为 `undefined`，校验通过 |

两处差异**不是「忘了补」，而是「补不出来」**：`usage` 与 `finish.replayState` 都由上游 provider 适配器在流末尾产出，掐断通过 `iterator.return?.()` 提前终止上游流，这两格从未产生（读代码确证，见 §四）。

**对 §九.3 那句断言的回答**：设计文档写的是「落盘的 `assistant/message` 与一次真实正常收尾**在结构上无差别**（否则下游消费者会看到异常）」。按本次取证——

- 断言**不成立**：存在稳定、可机检的两处字段差异（缺 `chunk:usage` 格 ⇒ 缺 `data.usage`；`finish` 无 `replayState` ⇒ `message.source` 缺键）。
- 但「下游消费者会看到异常」**只有部分成立**：不会报错、不会读不出、不会破坏自洽性；可见后果集中在 token 计量（§5.2）。
- 因此 §六 里「默认档位停在 `observe`」的理由仍站得住，但**理由需要改写**：不是「不知道下游会怎样」，而是「已知会丢 usage 与 replay 状态，量级可接受、且不可完全抹平」。

## 一、怎么触发的

### 1.1 一个反直觉的前置观察（实测）

任务书给的触发话术（「思考中每节之后单独占一行写『好。』」）在**干净的新会话里连试三次都没命中**：

| 尝试 | 会话 | 上下文量级 | 措辞 | 结果 |
|---|---|---|---|---|
| ① | 新建 `session-5df86d2a` | ~4.2 万 token | 「每节思考完之后，单独占一行写「好。」」 | 模型只在思考里**提到**要写「好。」，实际写在正文 |
| ② | 新建 `session-fb965b60` | ~4.2 万 token | 换成 2026-10-06 实测有效的原话 | 「好。」写在**正文**（`text` 块），思考段 283 字符 |
| ③ | 同 ② | ~4.3 万 token | 明确要求「全部在 reasoning 里完成」「夹在节与节之间」 | 思考段 542 字符，仍只把「好。」写进正文 |
| ④ | **打开历史会话 `session-ede7ff22`** | **~19 万 token** | 同原话模板，问一个新问题 | **一次命中两次**（turn 22 step 1、step 2） |

## 三、字段对照表

逐字段对照「掐断补块条」与「自然纯 reasoning 收尾」——两者块形状完全同类，差异全部落在 stream 尾部两格：

| 字段 | 掐断条 seq 1121 | 自然纯 reasoning 收尾 seq 718 | 差异 |
|---|---|---|---|
| `message.content` | `[{type:'reasoning',text:228}]` | `[{type:'reasoning',text:538}]` | 形状同，仅长度不同 |
| `message.role/id/source` | `assistant` / uuid / `{kind,provider,model}` | 同左 / `{kind,provider,model,replayState}` | **source 缺 `replayState`**（71 vs 247 字符） |
| `data.stream` 记录序列 | `chunk:block-start#0:reasoning` → `reasoning-chunks` → `chunk:block-end#0:reasoning` → `chunk:finish{stop}` | 同前三条 → **`chunk:usage`** → `chunk:finish{stop}+replayState` | **少 usage 格；finish 无 replayState** |
| `chunk:block-end.text` vs 落盘块 | `equal(228/228)` | `equal(538/538)` | 一致（触发点 chunk 照常放行的效果，§三.2 第 3 点） |
| `data.usage` | **无该键** | `{inputTokens:696, outputTokens:321, totalTokens:108153}` | **缺字段** |
| `finish.reason.kind` | `stop` | `stop` | 一致 |
| `finish.replayState` | **无** | 有（`{response:{kind:'deepseek-messages',…},blocks:[…]}`） | **缺** |
| `data` 顶层键 | `turn, step, message, stream` | `turn, step, message, usage, stream` | 少 `usage` |
| `step/end` 键 / `turn/end` 键 | `turn,step` / `turn,reason` | 同 | 一致 |
| 所在 turn 的 `turn/end.reason` | `{kind:"completed"}`（turn 22 @ seq 1137） | — | 一致（turn 粒度也伪装成功） |
| `interrupted` 标记 | **无** | 无 | 一致（见 §四，内核有该字段但掐断没用它） |

seq 1128（291 字符）与 seq 1121 逐字段同形；seq 1135、1090、1110 与 seq 718 同形（多一个 `text` 块）。

> **时间戳不能作为判据**。掐断条里 `chunk:block-end` 与 `chunk:finish` 落在**同一毫秒**
> （1121：均为 `1791307426507`；1128：均为 `1791307430570`），但这与自然收尾无法区分——
> seq 718 的 `block-end`／`usage`／`finish` 三格同为 `1791142203923`，seq 1135 的
> `usage`／`finish` 也同为 `1791307434344`。补块连发的两格与上游连发的两格在时间戳上没有可分性。
> 另一处相同点：两者的最后一条 `reasoning-chunks`（增量时间戳数组）都在，`time0` 到收尾间隔
> 同为秒级（1121 约 0.9 s，718 约 1.8 s）——**这一格也帮不上分辨**。

## 四、机理：为什么这两格补不出来

**读代码确证**（`.ssid-build/checkout/packages/…`，内核 `0.2.0-rc.1` 量级）：

1. **两格都源自上游适配器**。provider 适配器在流末尾产出 `usage` 与 `finish{replayState}`
   （`llm/llm-deepseek/src/translate.ts:161` 发 `finish` 时带上 `replayState(model, …)`）。
   掐断的 `finally` 里 `iterator.return?.()` 显式终止上游（`dsh-repeat-guard` `src/stream-guard.ts:88-95`），
   **这两格从未产生**——所以不是「补块漏了字段」，而是**上游数据不存在**。

2. **内核「有才写」**。`agent-loop/src/agent.ts:512-529` 组装落盘事件时：
   ```ts
   source: { provider, model, ...live.replayState !== undefined ? { replayState: live.replayState } : {} }
   …
   { turn, step, message, ...live.usage === undefined ? {} : { usage: live.usage }, stream: live.stream }
   ```
   `live.usage` / `live.replayState` 分别取自组装器累积的 `usage` 格与 `finish` 格的 `replayState`
   （`agent-loop/src/assistant-stream.ts:126-139`）。缺了就不写键——**不会填默认值、也不会报错**。

3. **`finish{stop}` 的 reason 本身是冗余的**：组装器的注释写着 "Terminal reason, **defaulting to stop
   when the stream omitted one**"（`assistant-stream.ts:131-134`）。掐断能补的只有这个默认值，真正
   补不出来的是 `replayState`。

4. **它走的是正常落盘分支**：`agent.ts:488` 判 `finish.kind`——`stop` 既不是 `error` 也不是 `aborted`，
   于是落 `assistant/message`（而非 `assistant/attempt`），`interrupted: true` 也不会出现
   （那只在 `signal.aborted` 分支，`agent.ts:449-465`）。**这就是「伪装成功」在内核侧的机理**。

5. **自洽性校验放行**：`session/session-persistence-jsonl/src/generation.ts:567-575` 会拿落盘字段与
   **从 stream 重放出来的组装器结果**逐项 `isDeepStrictEqual` 比对，不一致就抛错。掐断条两边同为
   `undefined`（`content` 也 `equal`）→ 校验通过。**所以日志能正常写入、正常读回**——这也解释了
   为什么本次实测的三条事件都干净落盘。

**推论（推理，非实测）**：任何**在下游补出这两格**的做法都要伪造 provider 数据（`replayState` 里含
reasoning `signature` 等不可重算的内容），因此「掐断痕迹可被完全抹平」在现行协议下做不到。

## 五、判定与下游后果

### 5.1 判定（实测 + 读代码）

- **判定：结构上有差别**，且是**可机检的稳定差别**：
  「`data.stream` 里没有 `chunk:usage` 格」等价于「`data.usage` 缺键」。隔离 dev 会话根全量扫描里，
  **5/5 掐断条成立、0/141 自然条成立**（`0eff13bb` 全量 141 条正常助手消息无一缺 usage 格）。
- **判定：块形状层面无差别**——`message.content` 与真实纯 reasoning 收尾同形，`step/end`、
  `turn/end` 也一致；**下游若只看块序列，无法区分**。

### 5.2 谁会读这些字段（读代码确证）

| 消费者 | 位置 | 缺 `usage` 的后果 |
|---|---|---|
| **每轮精确 token 汇总** | `llm/token-meter/src/turn-usage.ts:178` `deriveTurnTokenUsage` | 取 `event.data.usage ?? streamUsage(stream)`，两者皆无 → 该 attempt 无样本 → `closeOpen()` 失败置 `invalid` → **整个函数返回 `undefined`**（即：一个 turn 里只要有一处掐断，这轮的精确汇总就整体不可用） |
| **客户端回合尾部摘要** | `client/ui-chat/src/client/conversation-nodes/turn-tail.ts:90-99` | `tokenUsage === undefined` 时**不带该字段**——回合尾部的 token 摘要消失（**用户可见**） |
| **会话累计用量投影** | `llm/token-meter/src/usage-projection.ts:82-85, 192` | 有双重回退；`usage === undefined` 时只是**跳过更新**（保留上一次值），不置无效 |
| headless JSON 流 | `bundle/headless/src/json-stream.ts:191` `streamUsage(stream)` | 同样从 stream 取 usage → 拿不到 |

| 消费者 | 位置 | 缺 `replayState` 的后果 |
|---|---|---|
| DeepSeek 适配器重放 | `llm/llm-deepseek/src/replay.ts:49` | `source.replayState === undefined` → **直接返回 `undefined`**（无法重放这条消息） |
| pi-ai 适配器重放 | `llm/llm-pi-ai/src/replay.ts:247` | 走 `foreignAssistant(message)` 分支——**把这条消息当成「外来消息」** |
| 通用降级路径 | `llm/llm/src/index.ts:996` | `source.replayState === undefined` 时原样返回 |

**未实测的后果**：§5.2 全部由读代码得出，**没有在运行中的 UI 或重放流程里复现**（见 §5.4）。
`turn-tail` 的 token 摘要是否真的消失、重放分支是否真被走到，都还需要一次界面/流程实测。

### 5.3 「看起来像正常结束」这件事有多成功

- **turn 粒度**：turn 22 的三步（掐断、掐断、正常）收尾后，`turn/end` 的 reason 与正常 turn 完全一样（`{kind:"completed"}`）。
- **事件类型粒度**：落的是 `assistant/message`（不是 `assistant/attempt`），没有 `interrupted` 标记。
- **自洽性粒度**：种子校验（§四.5）通过，日志可正常读回。
- **唯一可分辨的痕迹**：stream 尾部少两格。**换句话说，下游若要识别「这一步是被掐断的」，现在只有这一条路。**

### 5.4 未验证面

1. **allostasis 自己实现的掐断未实测**。本次掐断由 `dsh-repeat-guard@0.2.2` 执行；三期落地后若照 §三.2 补同样的两格，落盘形状**应当**相同——但这是推理，不是实测。
2. **UI 可见性未实测**。回合尾部 token 摘要消失、以及界面上是否有其它差异，均只读代码、未在界面上复现。
3. **重放 / 重新生成路径未实测**。§5.2 那三条 `replayState` 分支的触发条件与实际表现未验。
4. **「短上下文不易触发复读」只是四次观察**（§1.1），未做统计；本次能一次命中两次，与 19 万 token 上下文相关，**因果未分离**（没有在同上下文下跑对照组）。
5. **`deriveTurnTokenUsage` 的返回值未在运行时验证**（只读代码，未构建 TS 环境实跑）。
6. **中途打断（`agent.cancel()` / `interrupted: true`）的落盘形状未对照**——本次样本里没有这种条。
7. **生成中解压未验**：三条样本都是在 `step/end`、`turn/end` 已落盘之后解压的；多帧 zstd 在写入途中的「半截帧」形态与本报告无关。
8. **多条掐断连续发生时的步号/续跑计数**未做边界核对（本次只看到连续两步）。
