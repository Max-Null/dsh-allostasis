# 应变三期：生成中掐断与重定向

> **缘起**：2026-10-06 的会话自锁事故暴露出一个缺口——**退化的代价是在一步之内付完的**，而应变现有的判据全部落在步骤边界（`agent/pre-step` / `agent/turn-stopping`）。等判据开口，几十万 token 已经烧完。本文设计第三期能力：在**生成过程中**判定、终止、重定向。
>
> 关联：`docs/排查/2026-10-06-展开调用爆栈与会话自锁.md`（事故记录）、`docs/设计/2026-09-28-应变二期-退化检测与自动干预.md`（判据来源）、`docs/设计/2026-09-29-压缩干预-重新设计.md`（三级阶梯）、`docs/设计/2026-09-30-空回合检测与可见化.md`（§九 steer 已验证）。
>
> 状态：**设计已定、未实现**。§九 列了动手前的待验证项。

---

## 一、要解决什么

二期把「退化」判出来了，但判出来之后**什么都来不及做**——因为退化的代价付在**一步之内**：

| 项 | t14/s4 实测 |
|---|---|
| 推理长度 | 368,074 字符 |
| 输出 token | 210,139（= 该步的流式增量数） |
| 生成耗时 | 8 分 10 秒 |
| 触发条件 | 上下文 651,841 token（65%），`maxTokens` 上限 256,000 |

更要命的是**曲线形状**（对这条推理按 5,000 字符分块、逐块算重复率）：

```
0–5,000 字符    68%   ← 正常分析与碎片交错
5,000 字符起    100%  ← 一路到底，占全文 98.5%
```

**退化的决定点在头 5 千字符内就完成了，剩下 98% 是惯性。** 而 `agent/pre-step` 要等这一步**结束后**才轮到它说话——那时 21 万 token 已经出去了。

所以三期要做的不是「更早地说」，而是**在生成中途把它停掉**。

## 二、方案来源：`dsh-repeat-guard`

这不是从零设计。DSH 生态里已有一个第三方插件做同一件事：

| 项 | 值 |
|---|---|
| 包 / 版本 | `dsh-repeat-guard` / 0.2.2（作者 yuqing，MIT） |
| 它解决的 | README 原文：「解决大模型用你的 token **唱歌**的糟糕问题」——「唱歌」是社区对这类退化的叫法 |
| 它的机制 | 包 `llm/stream` → 白名单判据 → 掐断 → `turn-stopping` steer 续跑 |
| 它的观察 | 「上下文长度达到 300k 以上时，该现象会变得十分频繁」「只出现于思考过程而不出现于回答内容」 |

### 2.1 离线回放：对我们那条退化流有效

用它的**真实判据代码**（`lib/detect.js` 的 `findDegenerateLine`）对本次事故的 368,074 字符逐行回放：

| 步 | 命中于 | 占比 | 掐断后省下 |
|---|---|---|---|
| t14/s4（事故那一步） | 字符 2,713 | **0.7%** | 36.5 万字符 / 21 万 token / 8 分钟 |
| t13/s8（首次退化） | 字符 656 | **1.2%** | 5.4 万字符 |

全量 225 条含思考的助手消息：首次命中 48 条，其中「命中后仍有思考」（它的防误报：命中行位于思考末尾属正常收尾，不拦）→ **会掐断 33 条（14.7%）**。

### 2.2 dev 实测：四个环节都跑通了

2026-10-07 在隔离 dev 实例（`home-100` / profile `ssid-dev`）上装该插件并验证：

| 环节 | 结果 |
|---|---|
| 加载 | `[repeat-guard] 已加载，复读拦截生效`；三个失败信号全 0 |
| 判据命中 | `检出思考段复读，已掐断本次生成 | 命中行="好。"` |
| 掐断 | 该步只产出 reasoning、无文本无工具调用 |
| 续跑 | `turn-stopping：会话 … 续跑一步`，随后该 turn 正常 `completed` |

### 2.3 它的两个边界（吸收时要各自处理）

1. **白名单覆盖有限**：不在 32 项表里的碎片形态不会被拦；而逐 chunk 全量重扫是 O(n²)——命中得早所以无恙（实测命中点单次 0.03 ms），**不命中时会空转**（全文单次 1.66 ms × 21 万 chunk）。
2. **干预率 14.7%**：被掐断的包括「思考中途说了句『好。』又继续想」这类正常步。作者在 README 里明说这是「不得不付出的代价」。

## 三、机制：三块 + 一块内部协调

### 3.1 流观测：挂 `llm/stream`

`llm/stream` 是**官方文档化的扩展点**，不是私有接口：

- 签名在 `packages/llm/llm/src/index.ts:75`，且进 `packages/extensions/tool-cordis/src/api-catalog.ts:4053`；
- 内核自己两处按同一形态使用：`session/session-title/src/index.ts:368`、`session/session-checkpoint-policy/src/index.ts:64`。

它是 waterfall，包一层上游流即可逐 chunk 观察：

```ts
ctx.on('llm/stream', (options, next) => wrap(next()), { global: true })
```

**只检测思考段**（`reasoning-delta`）。理由与 repeat-guard 同：复读先出现在思考里，等正文也碎掉再掐，思考段已经白烧一遍。辅助调用（`options.purpose !== undefined`，如会话标题、上下文压缩）不参与检测。

### 3.2 掐断：补块伪装成正常结束

命中后**不用 `agent.cancel()`**——那会作废整轮。做法是把这次生成**伪装成正常收尾**：

```ts
yield chunk                                            // 触发点照常放行
yield { type: 'block-end', index, block: { type: 'reasoning', text: accumulated } }
yield { type: 'finish', reason: { kind: 'stop' } }
return
```

三个不能省的细节：

1. **命中后要再探一格**：若下一格仍是 `reasoning-delta` → 说明思考在继续复读，拦；若换成正文、工具调用或直接收尾 → 命中行本来就是这段思考的最后一句，属正常收尾，**不拦**。没有这一格，正常步的结尾语会被误拦。
2. **`finally` 里必须 `iterator.return?.()`**：提前 return 时若不下传，上游 HTTP 流会继续跑到结束，**供应商照常计满 token**，且连接悬挂（repeat-guard 源码注释记录了这条）。
3. **触发点那个 chunk 照常放行**：否则 `accumulated` 与落盘的 `block-end.text` 会对不上。

### 3.3 重定向：`agent/turn-stopping` 里 steer

掐断只是让这一步**提前结束**，还得让机器继续走——否则 turn 就以「模型没说话」收尾。做法是挂在回合收尾边界上，在本轮提交之前推一条输入：

```ts
agent.steer(pluginNotice(resumeText, summary))
```

`agent/turn-stopping` 的契约写明：「a listener that objects steers and the machine re-reads its inbox: fresh steering runs another step」；而「Data decides, so listener order cannot change the outcome」。

**这条能力已经被验证过**：空回合设计 §九（`2026-09-30-空回合检测与可见化.md:177`）用同一机制验过「补生成能改变采样轨迹」；2026-10-07 的 dev 实测再次印证。

### 3.4 内部协调：自己掐断的静默不记为空回合

**这是把机制吸收进 allostasis（而不是继续依赖第三方）的最大收益。**

掐断之后那一步只剩 reasoning、没有文本也没有工具调用——**这恰好满足空回合判据**。实测（`steer` 档下）会让两个插件对同一次静默各 steer 一次，模型同时收到两条措辞相近的提醒：

| 来源 | 措辞 | 隐含动作 |
|---|---|---|
| 空回合检测 | 「用一两句话补上：这一轮得出的结论、以及下一步需要他做什么」 | 补一句给人看 |
| repeat-guard | 「请直接继续执行下一步，不要再输出任何确认语、寒暄或空话」 | 别废话，直接干 |

**吸收之后这个问题从根上消失**：同一次静默发生在同一个插件内部，掐断方自己知道「这一步是我终止的」，不需要任何跨插件协议。

判据形状：`turn-stopping` 里维护「本 turn 是否由本插件掐断过」，命中即跳过空回合判定与补生成。

## 四、判据：以统计为主，白名单退为辅助

本节初版写的是「两套都留、先到先掐」，依据是离线回放里两者命中时机接近（2,713 字符 vs 4,000 字符）。**全库回放推翻了这个结论**（2026-10-07，484 个会话 / 31,000 条含思考的助手消息）：

| 阈值 | 会掐断 | 干预率 | 涉及会话 | 提前量中位数 | 20k+ 长消息命中 |
|---|---|---|---|---|---|
| 1（发现即拦） | 9,217 | **29.73%** | 115 | 68.6% | 20 |
| 2 | 5 | **0.02%** | 4 | 43.2% | 0 |
| 3 | 3 | **0.01%** | 2 | 9.8% | 0 |

三点：

1. **不是权衡，是悬崖。** 阈值从 1 调到 2，干预率从 29.73% 掉到 0.02%（约 1500 倍）。原因是「连续命中」在这类碎片上几乎不存在——碎片之间总夹着不命中的行（如「**（！）**」），run 被反复清零。**白名单判据实际上只有「发现即拦」一个可用档位。**
2. **它拦到的绝大多数不是退化。** 29.73% 里只有 20 条是 20k+ 的长输出，**99.8% 落在短消息上**——即「绝大多数时候在打断正常步，而真正需要拦的长输出占 0.2%」。
3. **命中行分布**：「好。」占 62%（5,711 / 9,217），其次「执行。」1,787、「写。」1,085、「嗯。」519。这些是模型思考里的连接词，不是退化标志。

**所以三期的主判据必须是统计判据**（`measureRepetition` 的口径）：它测「这段内容有多少信息」，与输出长度相关，不在短正常步上误报。白名单退为**辅助信号**——在统计已判定后加速确认，或用于统计样本不足的早期窗口。

**另一个可用信号是输出长度本身。** 真退化是「一步之内烧掉十几万 token」，而误报里 99.8% 是短消息——**长度门槛**是廉价可靠的第一道筛子：它不需要读文本，只需要数已生成的字符数。

> **离线数字会低估在线行为**：上面这组数是拿历史日志（**最终文本**）回放的，而检测器在线看到的是**逐 chunk 的中间态**。实测同一批 225 条消息里，有 **4 条**「逐 chunk 判定会命中、对最终全文判定却不命中」——因为一行在某一刻可以是完整的表项（「好。」），随后被续写成长句（「好。现在开始」）。所以**在线干预率只会更高**，这组数是下界。

## 五、与既有能力的关系

### 5.1 三级干预阶梯要补一维

`2026-09-29-压缩干预-重新设计.md` 的阶梯是**按代价排的动作层级**（提醒 → 改变输入 → 压缩）。三期不在那个阶梯里，因为它是**另一个维度**：

| 维度 | 动作 | 发生位置 |
|---|---|---|
| 边界（既有） | 提醒、补生成、压缩 | 步骤之间 / 回合收尾 |
| **流内（三期）** | **掐断 + 重定向** | **生成过程中** |

两者时间轴不同，所以不是「第几级」的关系。**提醒是弱形式（说一句，听不听由模型），掐断是强形式（强制终止并重定向）**，作用于同一现象的早晚两个时点。

### 5.2 与一期、二期判据的关系

- 一期（语言漂移）不动：它的动作是锚定，与掐断无交集。
- 二期（推理退化提醒）**保留**：统计判据在步骤边界仍有价值（它能覆盖「掐断没拦到的、已经落盘的那些步」，例如首次命中的白名单未覆盖形态）。
- 空回合检测**保留**，但加一条例外（§3.4）。

### 5.3 「暂缓」的压缩干预不受影响

`compactRegion` 调用的暂缓结论（区间选择未决、误判代价偏高）**不因三期改变**——三期不删任何历史，也不动上下文。

## 六、开关与默认值

掐断是**能中断模型生成**的强动作，比注入一条提醒重得多，因此必须是配置项而不是常量：

| 档位 | 行为 |
|---|---|
| `off` | 不挂 `llm/stream`，与今天一致 |
| `observe` | 只判定与留痕（诊断行），不掐断 |
| `cut` | 掐断 + `steer` 重定向 |

**默认档位是 `observe`，不是 `cut`**（2026-10-07 定）。依据是 §四 的全库回放：白名单判据在自然条件下的干预率 **29.73%**，其中 **99.8% 落在短消息（正常步）上**——在判据换成统计口径并完成标定之前，默认掐断的代价（大约每三步打断一次）远大于收益。`cut` 保留给显式开启。

契约上应写清：任何档位下掐断都**不写新的会话事件类型**（铁律：下游插件的自定义事件类型会让整份日志被拒读，见空回合设计 §十一），留痕走 `console.debug`。

## 七、代价

| 代价 | 量 |
|---|---|
| **干预率** | 实测 14.7% 的含思考步会被掐断（含正常步），每次掐断让该 turn 多跑一步 |
| **性能** | 判据在流里逐 chunk 跑；repeat-guard 的白名单实现是 O(n²)（每个 chunk 重扫已生成文本），命中早所以无害，未命中时空转。**吸收时改用增量扫描**——已证与原实现等价（§九.2），且跑最长那条 21 万增量的流只要 0.6 ms |
| **责任面** | allostasis 从「观察 + 提醒」升级为「能中断生成」。这改变插件的定位，README 的「它做什么」需要相应重写 |

## 八、备选方案

| 方案 | 做法 | 取舍 |
|---|---|---|
| **A. vendor 它** | 搬源码进本仓库（先例：`dsh-better-sidebar` 走 vendored + `file:`） | 保留它的设计、能立刻改；但仍是一个独立插件，**交界还在**；跟上游更新是手工活 |
| **B. 吸收进 allostasis** | 把三块机制做进本插件 | **选定**。交界从根上消失（§3.4）；且 allostasis 本就是「判据 + 动作」型插件（一期锚定、二期提醒、空回合兜底都在同一插件内），加掐断是同型扩张 |
| **C. 继续依赖 + 加失效监测** | 写探针检测它是否还在工作 | 最省事，但失效是静默的，且我们发现得比用户晚 |

**为什么是 B 而不是 A/C**：本工作区对第三方插件有一条既有取向——「一个适配面一个插件，不合并」，但它的**重新评估触发条件**恰恰是「它们开始共享状态或生命周期」。三期正是这种情况的两个证据：① 掐断改变空回合判据的输入分布（§3.4）；② 两者的动作在同一次静默上重叠（§3.4 的两条提醒）。此外 DSH 在快速迭代，而 **`llm/stream` 的块协议形状（`block-end`/`finish`）是全套机制里最脆的一环**——这一点是判断，不是实测：事件名在官方 API catalog 里，块字段形状没有同等承诺。放在自己仓库里，版本漂移时能立刻跟。

**许可**：repeat-guard 是 MIT，吸收合法；落地时保留版权声明。

## 九、待验证清单

**动手前必须回答的**：

1. ~~**误报面**~~ → **已完成（2026-10-07）**。做法：用增量实现（③ 已证与原实现等价）对全部 484 个会话 / 31,000 条含思考消息回放，一次解压三档阈值同跑，55 秒。
   - **结论**：干预率与阈值不成比例（29.73% / 0.02% / 0.01%，见 §四），且九成九落在短消息上。**白名单不能作为主判据**，默认档位据此定为 `observe`。
   - **仍然缺的**：**统计判据在流上的误报面**——那才是三期真正要标定的对象。做法同上（同一次回放换成按指数增长的重复率增量计算），但需要一个可在流上增量维护的重复率实现（`measureRepetition` 现在是「对整段算一次」）。
2. ~~**增量扫描的等价性**~~ → **已完成（2026-10-07）**。增量实现（维护「已结束行的累计 run」＋「当前未收尾行的缓冲」，每次 push 只处理新增文本）与原实现在**首次命中的 chunk 序号与命中行文本**上一致：
   - 严格对照（≤ 5,000 字符的消息逐 chunk 双侧比）：**394 项全一致，0 不一致**；
   - 长消息（增量报命中 → 用原实现在该累积文本上复算）：16 项一致；
   - 长且不命中的 40 项**无法便宜地严格验证**，如实计入未验证面（逐 chunk 跑原实现是 O(n²)，这 40 项正是那样跑不动的那批）；
   - 对照总耗时 2.44 秒（第一版因为逐 chunk 跑原实现，十分钟跑不完）。
   - **一处必须照抄的细节**：原实现每次调用都会看到「尚未收尾的最后一行」（`split` 的最后一段），所以增量实现每次 push 之后要用**临时 run** 判一次未完成行，且**不能把它的 hits 累进 run**——否则同一行会被后续 chunk 重复计入。
3. **`block-end` / `finish` 的落盘形状**：断言「伪装正常结束」之后，落盘的 `assistant/message` 与一次真实正常收尾**在结构上无差别**（否则下游消费者会看到异常）。dev 实测里那条被掐断的消息只剩 reasoning——但没验证它与真实收尾的字段级差异。

**实现后要验的**：

4. **掐断的静默不再进空回合判定**（§3.4 的内部协调）。
5. **两条判据同时在场时的取先行为**（白名单先命中就不必再算统计）。
6. **与 `dsh-guardian`、`dsh-repeat-tool-reminder` 的交互**：后两者管的是工具调用层，理论无交集，需实测确认无重复动作。
