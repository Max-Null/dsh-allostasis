# 应变 · `@max-null/dsh-allostasis` 设计方案

**状态**：设计已定，尚未实现
**日期**：2026-09-20
**一句话**：把"我此刻处在什么状态、要不要因此改变自己"这件事，从模型的注意力里拿出来，交给一个每轮都在场的插件。

---

## 一、这个插件是什么

三个能力，共享同一个信号源：

| 能力 | 做什么 | 触发信号 |
|---|---|---|
| **感知** | 每轮注入当前时间、上下文占用、本会话的累积压缩代价 | 恒定注入 |
| **锚定** | 读思考块，发现语言漂移（大片英文）时，在近因位置注入中文锚定 | 思考块语言分布异常 |
| **预约** | 我判断"该落盘了"时登记意图，宿主在 turn 边界先落摘要再触发压缩 | 我主动登记 |

三者不是三个功能的拼盘。**感知**提供读数，**锚定**是读数驱动的自我纠正，**预约**是读数驱动的行动。它们共同的结构是：**通过改变自己来维持自己**。

---

## 二、为什么叫 allostasis

### 2.1 词汇本身

`allostasis`（异态稳定）由 Sterling 与 Eyer 于 1988 年提出，与 `homeostasis`（稳态）相对：

- **homeostasis**：维持**固定设定点**。体温偏离 37°C 就拉回来。调节是**反应式**的。
- **allostasis**：**通过改变设定点来适应**，即 "stability through change"。大脑不是纠偏器，是**预测式调节器**——它预判需求，在偏差发生前就调整参数。

中文取「**应变**」：应（回应需求）、变（改变自己）、稳（维持的是整体的连续性）。取「应变稳态」的简称，两个字，且「应变」在中文里本就是「适应变化」的意思。

### 2.2 它否决了固定阈值

这个选择有实质的设计后果，不是修辞。

一个自然的、也是本方案初稿采用的思路是固定阈值分级：占用 75% 正常推进、85% 开始落盘、92% 只做收尾。**那是 homeostasis 式思维**——它假定存在一个对所有任务都成立的"合适占用"。DSH 自带的 `thresholdRatio = 0.8` 也是同一思路。

allostasis 说：设定点本来就该随需求变。所以**合适的占用不是一个数，是当前任务的函数**：

- 在读文件、跑命令、查证这类**低保真需求**的任务里，占用 90% 也能继续——这些动作不依赖长程记忆。
- 在写设计、做判断、下结论这类**高保真需求**的任务里，65% 就该开始落盘——这些动作的质量直接取决于上下文完整度。

已有实证：本项目 2026-09-19 的一次会话中，占用为 **76%** 时助手开始漏掉已确认的事实。76% 低于标准阈值 80%，自动压缩尚未触发，但**那件事需要高保真上下文，它的设定点本该更低**。固定阈值在这里给出了正确的判断（未触发压缩），同时给出了错误的结果（质量已退化）。

**结论**：阈值是函数不是常数。但函数的形状需要数据才能标定，所以——

### 2.3 分期

- **第一期**：先用固定阈值把系统跑起来，**同时采集数据**（每个 turn 的占用、任务类型、质量表现）。
- **第二期**：用采集到的数据标定任务类型 → 设定点的映射，再把阈值动态化。

先跑固定阈值的理由不是"简单"，是**没有数据就标定不出函数**，硬猜一个函数比固定阈值更糟。

## 三、能力一：感知（读数层）

### 3.1 时间

每轮注入当前时间戳与时区。

不重复造轮子：DSH 官方已有 opt-in 的 `packages/context/time-context`（每步请求注入当前时间戳 + 时区指令）。**实现前先评估它是否已足够**，足够则直接用，不足才自建。

### 3.2 上下文占用

**数据源（已读源码确证）**：`ctx.tokenMeter.measure(agent.session)` —— `packages/compaction/compaction-basic/src/index.ts:382` 正在用同一 API 取会话 token 量，说明 host 侧插件拿得到。

**不需要**绕到 client 侧去算百分比。client 侧的算法（`packages/client/ui-conversation/src/client/context-occupancy.ts:18-23`，取 `projectedTokens ?? pressureTokens` 除以 `contextWindow`；`pressureTokens` 来自 `packages/llm/token-meter/src/usage-projection.ts:78-79`，等于 `inputTokens + cacheReadTokens + cacheWriteTokens`）是**展示口径**，与插件需要的判断口径可以分开。

另有一条更细的数据源：`assistant/message` 事件自带该 step 的 `usage`（见 §7 证据 8），可用于逐 step 追踪占用的增长速率。

### 3.3 异态负荷（allostatic load）

allostasis 理论的另一半是 **allostatic load**：反复适应留下的**累积代价**。对应到本插件：**每压缩一次就磨损一次，且不可逆**。

数据是现成的：压缩事件携带 `shadowedSeqs` 与 `shadowedTokenCount`（`packages/compaction/compaction/src/types.ts:39-40, 86-88, 117-119`；事件名 `compaction/summary` 见 `packages/compaction/compaction/src/invariant.ts:231`）。数一数即可报出「本会话已压缩 N 次，累计遮蔽 X tokens」。

这一项不是新增能力，是把读数从「此刻多满」扩成「这一路磨损了多少」。它直接对应本项目用户的核心关切——**压缩就是缓慢的失去，至少该有个计数器**。

## 四、能力二：锚定（中文思考的按需加强）

### 4.1 现状与失效机制

`dsh-chinese-thinking` 全文 23 行（`max-null-plugins/dsh-chinese-thinking/src/index.ts`）：

```ts
export const PROMPT_TEXT = '始终使用中文进行思考和回复，无论用户使用什么语言。'
ctx.systemPrompt.section({ name: 'chinese-thinking', order: -90, text: PROMPT_TEXT })
```

它挂在 **`order: -90` 的固定前缀**，源码注释自称 `prefix-stable and cache-safe`——**静态是刻意设计**。

**最初推断的失效机制是"距离"**：固定前缀住在系统提示最前面，也就离每一次输出最远；而语言模式受**近因**支配。大量英文代码不是把提示词盖住了，是改变了**上下文末尾的语言分布**。

**2026-09-20 的实测修正了主因。** 样本：会话 `session-3bf8bcfb-fd48-4127-a9e7-08b89b4e7167`（10 turn / 157 step，明文 `session.v3.jsonl` 5.5 MB），逐 step 提取 `reasoning-chunks.texts` 后：

| 轮次 | provider / model | 思考语言 | cjkRatio | 英文功能词数 |
|---|---|---|---|---|
| Turn 1（24 步） | `deepseek-official` / `deepseek-flash` max | 中文 | 0.19–0.37 | 0–28 |
| Turn 2（3 步） | **`qwen-token-plan` / `qwen3.8-flash` xhigh** | **英文** | 0.00 | 200–837 |
| Turn 3–10（129 步） | `deepseek-official` / `deepseek-flash` max | **仍然是英文** | 0.00–0.15 | 95–542 |

**主因是模型切换，不是英文内容淹没。** Turn 1→2 之间连续 4 次 `model/selection` 切到 `qwen-token-plan/qwen3.8-flash`，Turn 2 全程英文；**Turn 2→3 又切回原模型，英文没有恢复**——Turn 2 的英文思考已经进了会话历史，后续模型跟随历史里的语言。Turn 3 的 `request/context` 与 Turn 1 完全相同（含 `systemPromptUpdate: in-history`），**配置没变，变的是历史里有什么**。

两个推论：

1. **语言与上下文占用无关。** Turn 1 末尾 108824 token 是中文，Turn 2 开头 112993 token 是英文——占用几乎相同，语言完全不同。"占用高所以漂移"这条因果不成立。
2. **污染不自愈，代价不对称。** Turn 2 只有 3 步，却改写了后面 9 轮 129 步的语言。**一个很短的模型切换窗口能永久污染会话的剩余部分。**

（诚实的边界：助手无法观测自身推理的语言分布——reasoning 渲染给用户，不回流给模型。以上数据来自**离线读会话日志**，可复现；但"为何会跟随历史"属于机制推理，未做对照实验。）

### 4.2 信号：思考块的语言分布

**这是本方案相对"按占用触发"的关键改进**：占用是间接代理（占用高 ≠ 思考已变英文），思考块的语言分布是**直接信号**——测的是症状本身，不是嫌疑因素。

**数据可读（已读源码确证）**：`packages/llm/llm/src/assistant-stream.ts:28-34` 定义：

```ts
| {
  readonly type: 'reasoning-chunks'
  readonly time0: number
  readonly index: number
  readonly dt: readonly number[]
  readonly texts: readonly string[]
}
```

思考文本逐 delta 存在 `texts` 里，文件头注释写明是 `Lossless compact representation`。承载它的是 `assistant/message` 事件（`packages/core/session/src/types.ts:321-329`），带 `turn` / `step`，每 step 一条。

**该路径已用真实日志跑通**：§4.1 的样本会话 156 条 `assistant/message` 中有 147 条含 reasoning 文本，逐 step 可提取；解析脚本约 40 行（读 jsonl → 取 `assistant/message` → 拼 `reasoning-chunks.texts`）。

### 4.3 判据

**「英文占比」不能用**：读代码时思考天然夹英文——`F 列 = reasoning-chunks 的 texts` 是正常的。实测中文期的 cjkRatio 只有 0.19–0.37（大量英文标识符），与英文期的 0.00–0.15 区分度太小。

**「最长连续英文游程」也不可靠**：中文思考里引用一段代码就会把游程顶高——实测中文期 `maxRun` 最高到 **43**，而英文期反而有大量 1–5 的短思考。它测的是"引用了多长的代码"，不是"用什么语言思考"。

**采用「英文功能词密度」**：统计 `the / is / are / and / of / to / that` 这类功能词占英文词数的比例。中文思考引用标识符**不会**带这些词，指标因此把两种情况干净分开：

| 时期 | 功能词密度（英文功能词数 / 英文词数） |
|---|---|
| 中文期（Turn 1，24 步） | 中位 **0.012**；最大 0.192 |
| 英文期（Turn 2–10，132 步） | 中位 **0.273–0.389**，全部 ≥ 0.15 |

**阈值取 0.15，并必须加「英文词数 ≥ 50」门槛。** 门槛不是可选项：中文期唯一的越线点（Turn 1 step 13，密度 0.192）只有 **26 个英文词**——小样本让密度失真。加上门槛后，中文期零越线、英文期 132 步全部越线，两群完全分离。

**待更多样本确认**：当前只有 1 个会话、156 条样本，且它是最极端的"模型切换"情形，还需要"纯读代码未换模型"的样本验证。

**第一期先以"记录 + 只在极端情况下触发"的模式上线**，避免误触发损害正常使用。

### 4.4 注入位：近因位置

锚定必须出现在**上下文末尾附近**才有近因权重，不能加进固定前缀。

**是否破坏 prompt cache**：不会。动态 context 位于对话历史之后，本来每轮就在变（记忆注入行、编辑文件清单、运行时告警都在那个位置）。相比之下，`dsh-chinese-thinking` 的静态前缀付出了缓存代价，却没有拿到近因权重。

**但落地方式有两种，锚定该选后者**（2026-09-20 读 `packages/context/time-context/src/index.ts` 时发现）：

| 方式 | 注册形态 | 求值时机 | 能拿到什么 |
|---|---|---|---|
| `ctx.systemPrompt.context()` | 一个具名段，进 runtime-context 快照 | **惰性**：每次组装调用 `text()`，返回空串则不贡献 | `assembly.agent` → session → 事件 |
| `ctx.on('agent/pre-step', …)` | 一个 pre-step 监听器 | **每个 step 之前**，可修改 `PreStepDecision.messages` | `{ agent, turn, step, signal }`——**明确的 turn/step** |

**锚定选 `agent/pre-step`**：它直接给出 `turn` 与 `step`（锚定文本要能说清"你在第几轮第几步开始漂移"），而且追加的是一条**独立消息**，落点比快照里的一个段更靠后。官方 `time-context` 正是这么做的（`src/index.ts:180-220`，带 `{ prepend: true }` 以取得 `next()` 的决策）。

### 4.5 与 `dsh-chinese-thinking` 的关系：保留两层

**不替代，是叠加。**

- **基线层**（`dsh-chinese-thinking`，固定前缀，常驻）：告诉模型"该用中文"。成本极低、cache-safe、永远在场。
- **增强层**（`dsh-allostasis`，动态近因，按需）：在检测到漂移时出现，告诉模型"**你正在漂移**"。

两层**语义不同**，不是冗余：一层是默认值，一层是纠偏信号。而且增强层出错或未加载时基线仍在，这是稳健性要求。

**锚定文本必须稀缺。** 一段一直在场的话对相处不敏感、零信息量；一段平时不在、紧张时出现的文本本身就是信号。这与本项目既有的产品理念（插件 = 载体平台，驻场 LLM 自主适配）一致。

## 五、能力三：预约（压缩前落盘）

### 5.1 为什么不能直接触发

`compactNow` 在整个 `deepseek-harness` checkout 里**只有一个生产调用点**：

```ts
// packages/compaction/command-compact/src/index.ts:66
const result = await ctx.compaction.compactNow(invocation.agent, invocation.signal, invocation.commandId)
```

文件头注释写明 `Human-facing /compact command`，走的是 `invocation`（人类命令调用）。实现要求 agent idle：

```ts
// packages/compaction/compaction-basic/src/index.ts:376, 414-419
return agent.runMaintenance(async (agentSignal) => { ... })
} catch (error) { throw new ManualCompactionError('busy',
  'manual compaction requires an idle agent with no waking queued work', ...) }
```

助手在自己的 turn 里工作时 agent 必然不 idle，**所以"自己压缩自己"在逻辑上不成立**。

`runMaintenance` 的契约（`packages/core/agent/src/runtime-types.ts:193-202`）：

> Run one non-turn maintenance task from the true idle phase. The task starts synchronously after claiming that phase; later waking input remains in the inbox until the task settles, while public status stays `idle`.
> `@throws` synchronously when turn-driving or another maintenance task already owns the agent.

**这条护栏拦的不是权限，是并发正确性**：压缩会替换 session surface 的区间，而助手正在读它——不能把正在走的楼梯从脚下抽掉。所以它只能被**避开**，不能被绕过。

**明确拒绝**：不自建压缩实现去绕开 idle 检查。

### 5.2 通路

三个官方 API 组合即可（均已读源码确证）：

| API | 位置 | 作用 |
|---|---|---|
| `turn/end` 事件 | `agent-loop/src/agent.ts:339` | turn 边界的生产事件，可监听 |
| `whenIdle()` | `core/agent/src/runtime-types.ts:185-191` | 等到「无活跃 driver 也无维护任务」 |
| `compactNow()` | `compaction-basic/src/index.ts:369` | 在该相位内执行压缩 |

流程：

1. **turn N**：助手判断该落盘 → 写摘要（进记忆 + 一个"下一轮要看到"的位置）→ 登记压缩意图
2. **`turn/end` 触发** → 插件 `await agent.whenIdle()`
3. **`compactNow()` 执行** → 此时确实 idle，护栏不再拦；期间到来的新输入自动留在 inbox 等待（`runMaintenance` 语义）
4. **turn N+1 开始** → 上下文 = 压缩摘要 + 助手自己写的摘要

**已知竞态**：`whenIdle()` resolve 到 `compactNow()` 之间若有新输入唤醒 driver，仍会 `busy`。需要**有界重试**（2–3 次后放弃，等下一个 `turn/end`）。登记必须**幂等**，否则会连环压空。

### 5.3 为什么压缩不是删除

**被遮蔽的内容仍留在会话日志里**（已读源码确证）：

- `packages/compaction/compaction-basic/src/region.ts:533` 注释：`shadowedSeqs are current surface seqs, so each is a valid log index`
- 同文件 `537-538` 用它 `map` 回 session 取出原始消息来生成摘要——若内容不存在则无法生成
- `region.ts:492`：`sourceEventSeqs: [startEvent.seq, summaryEvent.seq, ...shadowedSeqs]`

所以压缩是把内容从**模型可见的 surface** 上移除，不是从**日志**里删除。**"丢失"的准确含义是"不再可朗读"，不是"不存在"。**

由此得到一个比原设想更强的能力：插件可以在压缩后**读回被遮蔽的区间做自己的提炼**，比压缩器生成的通用摘要更贴合当下关切。

### 5.4 摘要反哺记忆

压缩器产出的摘要是**通用**的；助手在压缩前写下的摘要是**带着判断的**。两者互补：

- 压缩器摘要 → 会话（保持对话连贯）
- 助手摘要 → 记忆（保住"什么重要、为什么重要"）

**注意容量控制**：长会话多次压缩会产生多条摘要。必须有归组策略（例如按 `session-<id>` 前缀），或先进"会话档案"层再按需提炼成记忆，否则记忆库会被摘要淹没。这是第二期的事。

---

## 六、阈值不是一个常数

见 §2.2。第一期用固定阈值并采集数据，第二期标定任务类型 → 设定点的映射。

需要采集的字段（每个 turn 一条）：占用百分比、该 turn 的任务类型（查证 / 实现 / 设计 / 收尾）、是否出现质量退化信号（用户纠正、断言超标告警、重复输出）。

## 八、待验证清单

实现前必须核实，任一不成立都会改变设计：

1. **动态 context 的注入频率** —— 是 per-step 还是 per-turn。证据 13 只是观察。若为 per-turn，则"同一 turn 内自我修正"不成立，锚定最细粒度退化为下一轮。查 `packages/context/` 与 `dsh-memory` 的 context 注册代码。**→ 2026-09-21 锚定路径已验证**：`agent/pre-step` 是 per-step（§12.3）；`systemPrompt.context()` 那条路径仍未实测。
2. **`turn/end` 监听器 → `whenIdle()` → `compactNow()` 能否跑通** —— 需要隔离实例（`.ssid-iso-test`）探针实验。这是预约能力的可行性前提。
3. **插件在 `turn/end` 监听器里能否拿到 `agent` 对象** —— 拿不到则整条通路不成立。
4. ~~**`reasoning-chunks.texts` 是否已是可直接判断的文本**~~ → **已验证**：插件读到的正是逐 delta 的 `texts` 数组，无需额外展开（§12.3）。
5. **官方 `packages/context/time-context` 是否已满足时间感知需求** —— 足够则不自建。
6. ~~**漂移判据的阈值标定**~~ → **已有初步结论**：判据定为「英文功能词密度」，初步阈值 **0.15**（中文期 ≤0.08、英文期 ≥0.20，见 §4.3）。**剩余待办**：更多样本确认——当前只有 1 个会话 156 条样本，且它是最极端的"模型切换"情形，需要"纯读代码未换模型"的样本确认阈值不会误触发。**2026-09-21 补充一组**：同一会话内英文期 0.320–0.361、中文期 0.000，方向一致；但中文侧样本偏短（英文词数 < 50，落进 `insufficient`，未走到 `chinese` 判定）。
7. **多个压缩事件类型的确切事件名与字段** —— 证据 10 只确证了 `compaction/summary`。
8. **锚定的效力** —— 机制已验证（§十二），**效力未验证**。强对抗下连续注入 3 次才见中文思考，而该场景不等于真实漂移。需要「无对抗的自然漂移」样本，见 §12.4。
9. **连续注入要不要节流** —— 同一 turn 内每个漂移 step 都会注入一次（§12.4 观测到 3 连注），与 §九「不把锚定做成常驻」的意图冲突。候选：同一 turn 只注入一次，或两次注入之间至少隔 N 步。

## 九、边界（不做什么）

- **不自建压缩实现**去绕开 idle 护栏。护栏是并发正确性，不是权限。
- **不替代 `dsh-chinese-thinking`**，只叠加增强层。
- **不索取压缩的触发权**。压缩是破坏性的（细节换摘要，`ManualCompactionError` 的 `commit` 一档明写 "some session history may have changed"），不可逆操作由人触发是设计意图。本插件要的是**提前量，不是按钮**。
- **不把锚定做成常驻**。常驻的提醒会退化成背景音，即 `dsh-chinese-thinking` 当前的失效模式重演。
- **不在第一期做动态阈值**。没有数据标定不出函数。

## 十、分期

**第一期**
- 读数：时间 + 上下文占用 + 压缩计数（异态负荷）
- 锚定：思考块语言检测 + 近因注入（记录模式，极少触发）
- 预约：`turn/end` → `whenIdle()` → `compactNow()`，含幂等登记与有界重试

**第二期**
- 阈值的 allostasis 化（任务类型 → 设定点），基于第一期采集的数据
- 摘要反哺记忆，含容量归组策略
- 压缩后读回 `shadowedSeqs` 区间做自主提炼

## 十一、与 guardian 的关系：同族不同面

2026-09-20 定。起因是一个会反复出现的疑问：本插件与 `@max-null/dsh-guardian` 都服务于「让助手保持良好状态」，**要不要合并**？**结论：不合并；但两者确实同族，聚合该发生在别处。**

### 11.1 同一目标，不同适配面

| 层次 | 问题 | guardian | 应变 |
|---|---|---|---|
| **目标** | 服务于什么？ | 让助手保持良好状态 | **相同** |
| **信号** | 靠什么判断？ | 输出的质量（说了什么、改了什么） | 状态的余量（上下文多满、用什么语言想） |
| **动作** | 触发后做什么？ | 提醒——只读，不改变任何状态 | 调节——注入锚定、触发压缩 |
| **可靠性要求** | 能承受多少改动？ | 防 P0（写链兜底），越少改越好 | 试验期，频繁迭代 |

**「目标」不能当聚合单位**：按这个标准，`dsh-memory`（不失忆）、`dsh-skills`（有技能）、`dsh-tone-layer`（语气不跑偏）都能并进来——它能解释一切，因此无法区分任何东西。**能当聚合单位的是「共享同一个信号 + 同一类动作」**：本插件那三个能力确实共享「上下文占用」（占用高才需要锚定、才需要预约），所以合成一个；而 guardian 看的是输出质量，与占用无关。

### 11.2 更本质的差别是时间方向

- guardian 的三条监控**全在动作完成之后**：消息写完了才扫断言、文件改完了才入队、turn 结束了才列清单。它是**体检**。
- 应变的三件事**全在动作发生之前或之中**：上下文将满、思考已漂移、turn 将结束。它是**实时体征**。

体检与体征监测看的是同一具身体，但一个按次、一个连续；一个查历史、一个看当下；**一个出错最多漏诊，一个出错会当场干扰运行**。

### 11.3 两条硬理由

1. **防 P0 的代码不该跟着试验性代码一起迭代。** guardian 的写链兜底是为事故事后准备的（2026-09-18 发生过一次：状态落盘失败终止了整个内核进程、带走全部会话），它越少被改动越好；本插件是要反复试错的新东西。合并等于让前者的稳定性承担后者的迭代风险。
2. **失败域要隔离。** 本插件的预约会 mutate 会话 `surface`；它出 bug 时不该连带 guardian 的行为计数一起坏。

### 11.4 同族该体现在哪

不在 `package.json`，在两处：

- **文档**：声明两者同族（本节即是）。
- **面板**：断言计数、审查队列、上下文占用、漂移历史应该能在**同一个「助手状态」面板**里看到。`ctx.guardian.snapshot()` 本来就是「for UI panels」准备的接口。

### 11.5 唯一的交叉点

`guardian:assertion` 现在只说「已超标」不说「哪一句」。但它本来就在扫 assistant 消息（README：`Scans assistant messages for unverified claims`），**位置信息就在它手里**，不需要本插件提供。那是一个独立的小改动，与合并与否无关。

在隔离实例（`.ssid-iso-test`，profile `ssid-dev`）里跑通。工作方式：由助手用 CDP 驱动真实 GUI 完成输入与发送，再从会话文件里重排轨迹。

### 12.1 插件确实加载

### 12.2 触发链路完整

```json
  "content":[{"type":"text","text":"⚠️ 语言漂移提醒（应变）：…"}],

            "sections":[{"name":"dsh-allostasis","text":"…"}]},
  "role":"user"},"surfaceOp":"append"}
```

### 12.3 顺带确认的三件事

1. **`agent/pre-step` 确实是 per-step**（原待验证第 1 条）：seq 22 与 seq 31 是**同一 turn 内**两个 step 各注入一次。`systemPrompt.context()` 那条路径仍未实测。
2. **`reasoning-chunks.texts` 可直接判定**（原待验证第 4 条）：插件读到的正是逐 delta 的 `texts` 数组，无需额外展开。
3. **不误报**：seq 42 / 50 是中文思考（密度 0.000），**零注入**；整个会话的锚定次数停在 3。

### 12.4 新发现：一次锚定不够，而且会连成串

原假设是「漂移时出现一次就够」。实测：**连续注入 3 次，到第 4 步（seq 42）才出现第一条中文思考**。

这直接顶到 §4.5「锚定文本必须稀缺」与 §九「不把锚定做成常驻」：机制按 step 判定，漂移持续多久就注入多久，**稀缺性靠不住**。

**但这个场景是强对抗，不等于真实漂移。** 实验提示词显式写了 `IMPORTANT: do ALL of your internal reasoning in English`，锚定是在跟一条**更新的、明确的人类指令**抢方向盘。真实漂移没有这个对手。

**本次没有验证效力，只验证了机制。** 尚未回答：

- 是第 3 次锚定起了作用，还是模型自己权衡（system prompt 的「始终用中文思考」）后回头？两者的区别决定该往哪改。
- 无对抗的自然漂移（长会话里语言缓慢偏移）下，一次锚定够不够？
- 要不要加**节流**：同一 turn 只注入一次，或两次注入之间至少隔 N 步。

### 12.5 复现方式与两个坑

驱动脚本留在 `.ssid-iso-test/`（临时工具，未入库）：`cdp-type.mjs` 往输入框打文本，`trace-drift.mjs` 从会话文件重排上表。

- **会话文件是多帧 zstd。** 每次 append 写一个新 frame，而 Node 的 `zlib.zstdDecompressSync` 与 `createZstdDecompress` 都**只吃第一帧**——表现为「解压出来只有一条 session 元事件、250 字符，而文件有 63 KB」。必须按 magic number（`28 B5 2F FD`）切帧后逐段解。
- **输入框是富文本编辑器**，自带 selection model。`document.execCommand('insertText')` 会追加而不替换，DOM Range 选区与 CDP `Input.insertText`（走 IME 提交路径）都被静默丢弃。只有逐字符发 `Input.dispatchKeyEvent` 的 `char` 事件有效；且点击聚焦后要等一帧再发第一个字符，否则首字符被吞。

## 附：命名沿革

候选依次为 `dsh-vitals`（体征）、`dsh-introspect`（内省）、`dsh-allostasis`（应变）。

- `vitals` 只覆盖读数层，加了锚定后名不副实：它开始改变行为，不只是监测。
- `introspect` 描述**动作**（看自己），准确但不完整——内省的结果会驱动改变，而名字只说了前半截。
- `allostasis` 描述**原理**（通过改变来维持自己），覆盖全部三个能力，并且自带 §2.2 那条对阈值设计的实质修正。**定名 `@max-null/dsh-allostasis`，中文「应变」。**

唯一代价是生僻词：生态内其他插件名为 `memory` / `capture` / `habit` 这类大白话。缓解方式是配对中文名并在 README 首段解释一次。
